# M0 验证报告（macOS 部分）

> 日期：2026-11-10
> 环境：Apple M6，12 核，macOS 27.0.1，内建 60 Hz 屏幕（3072×1920，缩放 2×），Rust 1.99.1，.NET 10.0.401，Avalonia 12.1.6，quinn 0.11.12
> 代码：`spikes/s1-present`、`spikes/s2-transport`、`spikes/s3-pipeline/mac`

## 结论

| 项 | 状态 |
|---|---|
| S2 传输 | **通过**，并发现 pacing 公式需要修改 |
| S1 呈现（macOS） | **主要项通过**；真实上屏时间无法测量，工具条点击和跨屏 DPI 未测 |
| S3 管线（macOS） | **编码到 GPU 绑定通过**；真实屏幕采集未测 |
| S1、S3（Windows） | **未做**，需要一台 Windows 机器 |

设计的两个最大风险（quinn 能否绕开拥塞控制、Avalonia 能否内嵌低延迟视图）在 macOS 上都已排除。Windows 上的呈现行为（子窗口能否独立翻转）和硬件编码器仍是未知项。

## S2 传输

单进程两个 QUIC 端点，用户态弱网代理。所有结果都在**回环**上，没有真实网卡、Wi-Fi 或瓶颈链路。

### 通过标准

| 检查 | 标准 | 结果 |
|---|---|---|
| 120 fps、100 Mbps 不被 quinn 阻塞 | 无阻塞 | 0 次等待，0 次跳帧 |
| quinn 增加的 P99 延迟 | < 1 ms | 0.40 ms（裸 UDP P99 0.076 ms，quinn 0.48 ms） |
| 并发可靠流 P99 | ≤ RTT + 2 ms | 回环 0.29 ms；20 ms RTT 下 10.4 ms |
| 2% 丢包 + RS 25% | 完整率 > 99.9% | 100%，恢复 2188 个分片，0 损坏 |
| 中途切换路径 | 中断 < 100 ms | 9.2 ms，连接不断 |
| 固定 1200 MTU | 线上 ≤ 1200 | 线上最大 1200，`max_datagram_size` 1162，分片 1134 |
| 收包抖动（P99−P50） | ≤ 1 ms | 专用线程 0.38 ms，tokio 线程 0.20–0.41 ms |
| TLS exporter 两端一致 | 一致 | 一致 |

### 其他实测

| 场景 | 结果 |
|---|---|
| 2% 丢包、无 FEC | 帧完整率仅 **17.4%**（每帧约 92 包，说明 FEC 不可省） |
| 突发丢包（Gilbert 模型）+ FEC 25% | 100% |
| 故障转移（路径黑洞，1 s 检测） | 中断 1042 ms，检测后 27 ms 恢复，期间丢约 10% 帧 |
| 482 Mbps 压力（含 FEC） | 无跳帧，100% 完整 |
| FEC 编码 CPU（129 Mbps） | 10 秒累计 35 ms |

### 对照实验

| 配置 | 完整帧 | 包延迟 P50 |
|---|---|---|
| 自定义控制器，2% 丢包 | 1200/1200 发出 | 10.2 ms |
| **quinn 默认 Cubic，2% 丢包** | **仅发出 48/1200**，跳过 1152 帧 | **912 ms** |
| 默认 Cubic，无丢包，20 ms RTT | 1196/1200，有 1238 次缓冲等待 | P99 25.8 ms |

### 发现

1. **Pacing 公式错误**（已修订 §4.9）。`min(帧间隔 × 0.5, 帧字节 × 8 ÷ (1.5 × target))` 里的 target 是编码码率，不是链路容量，120 fps 下每帧总要摊 4.17 ms。回环上帧完成 P50 为 3.98 ms，几乎全是 pacing。改按 800 Mbps 链路容量后降到 2.39 ms。
2. **发送预算偏乐观**（已修订 §7.3）。macOS 没有 GSO，92 个包逐个系统调用，即使不限速也要约 2.4 ms。Windows 有 USO，可能更好，待测。
3. **丢包下可靠流的尾延迟**。2% 丢包时输入流 P99 从 10 ms 升到约 33 ms（重传 + ACK 延迟）。按键可接受，鼠标点击会有感知。
4. 专用接收线程与 tokio 线程的抖动没有明显差异。
5. **STUN 分流不能只看首字节**（M0 之后的集成测试发现，已修订 §4.1）。quinn 默认 grease QUIC 固定位，约 3% 的短头包首字节落在 `0x00–0x03`，被误当 STUN 丢弃。S2 原型没有分流，因此没有暴露。必须同时校验 magic cookie。修复后集成测试由 10 次过 1 次变为 20 次全过。

## S1 呈现（macOS）

Avalonia 12.1.6 + NativeAOT，Rust 线程用 Metal 在 `NativeControlHost` 的 NSView 上绘制。

| 检查 | 结果 |
|---|---|
| 句柄 | `NSView`，attach 返回 0 |
| UI 线程卡 500 ms | **视频不停**：其间提交 55–60 帧，最大帧间隔 16.5–16.9 ms |
| `displaySyncEnabled = NO` | 提交帧率从 60 升到 116–120（窗口），不限速时窗口 211–226、全屏 898–986 |
| 工具条覆盖视频 | 窗口和全屏 Space 内都可见（截图 + 窗口列表确认） |
| 调整大小 | 6/6，drawable 尺寸正确 |
| NativeAOT 反向回调 | Rust 线程回调 90+ 次，全部成功投递到 UI 线程 |
| 发布体积 | 约 35 MB（不含 dSYM，未压缩） |

**未能验证**
- **真实上屏时间**：`presentedTime` 在所有配置下均返回 0（回调本身每帧触发）。上面都是提交帧率，不是上屏帧率。本机屏幕只有 60 Hz，高刷效果也无法观察。需要高速摄像机。
- **工具条点击**：未自动化，需要人工确认。
- **跨屏 DPI 变化**：只有一块屏幕。
- 窗口模式下 `nextDrawable` 偶发阻塞约 17 ms，疑似 WindowServer 合成节拍，全屏下最大约 7–15 ms。

### 补充：鼠标事件能否穿过原生视频视图（2026-11-10）

在 S1 中让窗口上部为 Avalonia 区域、下部为原生视频视图，在进程内构造 NSEvent 交给窗口分发（与真实点击走同一条 AppKit 命中测试路径，不影响系统其他部分）：

| 区域 | 点击 | 滚轮 |
|---|---|---|
| Avalonia 区域（对照） | 收到 | 未收到（测试坐标换算偏差） |
| 原生视频视图 | **收到** | **收到** |

结论：点击和滚轮会沿响应链到达 Avalonia 窗口，App 在窗口层统一转发是可行的。鼠标移动无法用此方法验证（对照组也收不到），需要真实使用确认。跨进程 `CGEventPostToPid` 的尝试对照组也收不到点击，结果作废。

## S3 管线（macOS）

输入是**合成**的 IOSurface 帧（1080p，滚动纹理 + 移动色块），所以**不包含屏幕采集**。这部分用 Swift 编写，回答的是系统能力问题，VideoToolbox 的 Rust 绑定未验证。

### 延迟（编码 + 解码 + GPU 绑定，ms）

三次运行中两次完整结果的范围。一次运行中 H.264 低延迟 P99 达 25 ms，当时桌面有其他负载。

| 配置 | 编码 P50 | 解码 P50 | GPU P50 | 合计 P50 | 合计 P99 |
|---|---|---|---|---|---|
| H.264 低延迟 60 fps | 4.7–4.9 | 0.7 | 0.4–0.8 | 5.9–7.2 | 11.7–25.4 |
| HEVC 低延迟 60 fps | 4.7–4.9 | 0.6–0.7 | 0.5 | 5.8–6.0 | 9.2–12.3 |
| H.264 低延迟 120 fps | 4.6–5.5 | 0.7–1.3 | 0.5–0.6 | 5.9–7.5 | 8.7–9.5 |
| HEVC 实时（非低延迟）60 fps | 3.1 | 0.6 | 0.5–2.7 | 4.2–6.4 | 9.5–10.2 |

设计目标是 macOS 1080p60 总和 ≤ 35 ms。已测段约 6 ms，加网络/发送 2.4–4 ms；**采集和实际上屏未测**，因此目标尚不能判定。

### 待验证项答案

| 问题 | 答案 |
|---|---|
| HEVC 能否走低延迟码控 | **能**。文档“Only High profiles”不代表只有 H.264；之前的推测是错的 |
| LTR 与低延迟同开 | **能**，H.264 和 HEVC 都可以 |
| LTR 恢复效果 | 丢 3 帧后 `ForceLTRRefresh`：无 IDR，恢复帧 1.2–1.3 倍均值，PSNR 46.9–47.5 dB |
| 对比强制 IDR | 恢复帧 **56 倍**均值 |
| 非低延迟模式的 LTR | **不支持**（`EnableLTR` 返回 -12900） |
| H.264 丢帧后 `frame_num` 跳变 | 解码器**不报错，但画面损坏**（PSNR 15 dB 且不恢复） |
| 硬件 4:4:4 编码 | **不支持**。输入 4:4:4 仍输出 `chroma_format_idc=1`，SDK 无对应档次 |
| AV1 | 仅硬解，无硬编 |

### 配置细节

- `MaxFrameDelayCount` 所有模式都被拒绝（-12900）。
- 低延迟模式拒绝 `PrioritizeEncodingSpeedOverQuality`，尽管头文件推荐它。
- 实时模式 `MaxKeyFrameInterval = 0` 仍每 30 帧出一个关键帧；低延迟模式全程 1 个关键帧。
- 解码输出不指定像素格式时，Apple Silicon 返回 GPU 压缩缓冲，CPU 读取会崩溃。

## 设计修订

已写入 `DESIGN.md` 和 `DETAILED_DESIGN.md`：

1. Pacing 改按链路容量估计（§4.9）。
2. 发送延迟预算 ≤ 1 ms 改为 2–4 ms（总体设计 §7.3），总和 10–23 ms。
3. Mac 被控端所有模式统一用低延迟码控，HEVC 优先，LTR 开启（§6.5）。
4. Mac 被控端办公模式只有 4:2:0，靠静止精修补偿（§6.5）。
5. 确认必须用 `ref_epoch` 门控解码：硬解不会替我们报错（§6.3）。
6. STUN 分流增加 magic cookie 校验（§4.1）。
7. 活跃路径增加 250 ms 心跳，否则静止画面时会误触发故障转移（§3.3、§4.5）。

## 需要用户处理

1. **系统权限弹窗**：S1 第一轮调用 `screencapture` 时，macOS 弹出了询问 “Claude” 能否绕过系统窗口选择器访问屏幕和音频的对话框。未代为操作。真实屏幕采集测试（ScreenCaptureKit）需要这项权限，或由你手动运行测试程序并授权。
2. **Windows 验证机**：型号确定后可做 S1、S3 的 Windows 部分。
3. **高速摄像机测试**（可选）：唯一能给出真实端到端延迟的方法。

## 复现

```bash
cd spikes/s2-transport && cargo run --release
```

```bash
cd spikes/s3-pipeline/mac && xcrun swiftc -O -swift-version 5 -o s3-mac main.swift && ./s3-mac
```

S1 需要先 `cargo build --release`（`native/`），编译 `tools/winlist.swift` 到 `out/winlist`，再 `dotnet publish -c Release -r osx-arm64 -p:PublishAot=true`（`app/`），设置 `S1_OUT=<out 目录>` 后运行。
