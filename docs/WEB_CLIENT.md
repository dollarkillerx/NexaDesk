# NexaDesk Web 端方案

> 状态（2026-11-15）：已实现。浏览器（桌面和手机）在局域网和 Tailscale 中直接连被控端（§11），或经自建 `nexa-signal` 服务器从任何网络连接（§12）。网页走 HTTPS；支持输入法、触控手势和屏幕键盘、双向剪贴板（文字）。用演示主机在 Chrome 中做了端到端自动化测试（含模拟触控、输入法和剪贴板），直连和经服务器两条路径都通过；经服务器的一条在公网服务器上实测（浏览器和演示主机在同一台 Mac 上，画面经服务器 TURN 中转，往返约 20 ms）。真实手机、Safari、Firefox，以及用真实被控端（nexa-agent）经服务器接浏览器，尚未实测。

目标：不安装任何软件，用手机或 PC 浏览器控制一台 NexaDesk 被控端。

## 1. 结论

| 问题 | 决定 | 理由 |
|---|---|---|
| 传输 | **WebRTC** 为主 | 浏览器里唯一能打洞的方式；WebTransport 只能连接可直达的服务器 |
| 被控端实现 | Rust `str0m`，新增一个 `FrameSink` | 无需引入庞大的 libwebrtc；`FrameSink` 接口已预留 |
| 视频 | H.264 媒体轨道（RTP） | 手机上硬解最稳；丢包恢复用浏览器自带的 NACK/PLI |
| 输入 | DataChannel：按键可靠有序，鼠标不可靠无序 | 对应原生端的流和数据报 |
| 身份 | SPAKE2（WASM）并绑定 DTLS 指纹 | 与原生端同样的安全目标 |

**WebTransport 作为第二阶段优化**：只用于局域网和 Tailscale 这类可直达的场景。

## 2. 为什么不能直接复用原生协议

原生端用的是自定义 UDP socket、打洞和双向 TLS 证书。浏览器不开放这些能力：

| 能力 | 原生端 | 浏览器 |
|---|---|---|
| 原始 UDP / 打洞 | 有 | 只有 WebRTC ICE |
| 自定义 QUIC | 有 | 只有 WebTransport（基于 HTTP/3，需连到可直达的服务器） |
| 双向证书身份 | 有 | 无，改由应用层认证 |
| 全局快捷键 | CGEventTap | 受限，Cmd+Tab 等系统键拦不住 |
| 系统剪贴板 | 完全控制 | 需要权限和用户手势 |

## 3. 方案比较

| | WebRTC（媒体轨道） | WebRTC（DataChannel + WebCodecs） | WebTransport + WebCodecs |
|---|---|---|---|
| 穿越 NAT | ICE / TURN | ICE / TURN | 不能，需可直达或中继 |
| 浏览器覆盖 | 最广 | 广 | Safari/iOS 需 26.4 起（由系统版本决定） |
| 延迟 | 有浏览器抖动缓冲，需实测 | 可控，接近原生 | 可控，接近原生 |
| 手机解码 | 平台硬解 | WebCodecs | WebCodecs |
| 复用现有 FEC/重组 | 否 | 可以（移植到 WASM） | 可以（移植到 WASM） |
| 工作量 | 最小 | 中 | 中，还需 HTTP/3 + WebTransport 服务端 |

**推荐路线**：先做媒体轨道，最快可用；如果实测延迟不够，再换 DataChannel + WebCodecs，被控端的 `FrameSink` 和控制消息都不用变。

## 4. 架构

```
浏览器（PC / 手机）                         nexa-agent
┌────────────────────────┐                ┌──────────────────────────┐
│ <video> ← H.264 轨道    │ ←─ RTP/SRTP ── │ WebRtcSink（FrameSink）   │
│ 触屏/键鼠 → DataChannel │ ─ SCTP/DTLS ─→ │ 输入 → 现有 Injector      │
│ SPAKE2（WASM）          │                │ nexa-auth                │
└──────────┬─────────────┘                └────────────┬─────────────┘
           └────────────── nexa-signal（SDP/ICE）──────┘
                          TURN（直连失败时）
```

被控端的改动很小：

- 采集和编码完全不变。Web 会话协商 H.264 即可，Apple 被控端的低延迟码控支持它（M0 实测）。
- `WebRtcSink` 实现 `FrameSink`，把 Annex-B 帧交给 `str0m` 打包。码流形式在设计时就定为 Annex-B，正是为了这里。
- 浏览器的 PLI/NACK 映射到现有的 `force_idr` 或 `invalidate_from`。
- 拥塞控制使用 `str0m` 的 BWE，再喂给编码器的 `set_bitrate`。

依赖：`nexa-signal`（信令）必须先完成，原生端的公网连接也需要它。

## 5. 编解码

- **只用 H.264**。Safari 的 WebCodecs 对 HEVC 有过 `isConfigSupported` 返回 true 但解码失败的报告，H.264 最稳妥。
- 手机浏览器的硬解能力和低延迟表现需要在真机上测。

## 6. 手机交互

这部分是 Web 端和桌面端差别最大的地方，建议单独设计：

| 手势 | 映射 |
|---|---|
| 单指点按 | 左键点击 |
| 单指拖动 | 模式可切换：移动光标（触控板模式）或直接拖动（触摸模式） |
| 双指点按 | 右键 |
| 双指滑动 | 滚轮 |
| 双指捏合 | 本地缩放画面，不发给被控端 |
| 虚拟键盘 | 组合输入提交后走 `TextInput`，另设 Ctrl/Cmd/Esc/方向键工具条 |

## 7. 浏览器限制

| 限制 | 影响 | 应对 |
|---|---|---|
| 系统快捷键拦不住 | Cmd+Tab、Win 键等到不了被控端 | 工具条按钮；Chromium 全屏时用 Keyboard Lock API |
| 剪贴板需要用户手势和权限 | 自动同步受限 | 粘贴事件触发时同步；iOS 上退化为手动按钮 |
| 页面进入后台 | iOS 会暂停 | 回前台时重连并请求关键帧 |
| 没有指针锁（手机） | 游戏模式不可用 | Web 端只提供办公模式 |
| 组合键改写 | 浏览器能拿到 `KeyboardEvent.code` | 复用 `nexa-input` 规则（编译为 WASM） |

## 8. 安全

- 浏览器没有设备密钥存储，首次连接必须用一次性码；可用 WebCrypto 的不可导出密钥保存身份，但清除站点数据后需要重新配对。
- SPAKE2 必须绑定 DTLS 指纹，否则信令可以中间人。
- **Web 页面本身在信任链上**：托管页面的服务器被攻破，就能下发恶意脚本窃取一次性码。建议支持自托管，并使用 SRI 和严格的 CSP。
- 必须走 HTTPS；局域网场景需要解决证书问题。
- 被控端的确认弹窗和会话提示同样适用，并显示“来自浏览器”。

## 9. 里程碑

| 阶段 | 内容 | 退出标准 |
|---|---|---|
| W0 验证 | `str0m` 推 H.264 到 Chrome、Safari、iOS Safari | 真机延迟数据；决定媒体轨道还是 WebCodecs |
| W1 | 信令、认证、桌面浏览器看和控 | PC 浏览器可完成办公操作 |
| W2 | 手机手势、虚拟键盘、前后台恢复 | iOS 和 Android 真机可用 |
| W3 | 剪贴板、TURN、局域网 WebTransport（可选） | 对外试用 |

## 11. 第一版实现（与方案的差异）

**不需要服务器。**原方案经 `nexa-signal` 交换 SDP。产品方向改为默认无服务器、跨网络推荐 Tailscale 之后，被控端自己在一个 TCP 端口（默认 47801，和原生端的 47800 相邻）上提供：

- 网页本身（`crates/nexa-web-page/web/`，编译进二进制）；
- `/ws`：一条 WebSocket，承载信令和配对。

所以浏览器能连到的范围和原生端不经服务器时一样：同一局域网，或同一 tailnet。

```
浏览器                                被控端（nexa-agent --web）
  GET /  ────────────────────────▶  网页、脚本、pake.wasm
  WS /ws：offer SDP  ─────────────▶  str0m 应答；开始 SPAKE2
         ◀── answer SDP、SPAKE2 第一条
         SPAKE2 回复、确认值  ──────▶  核对，绑定双方 DTLS 指纹
         ◀── waiting                 本机弹出确认窗口
         ◀── accepted、确认值          浏览器反过来核对被控端
  ═══ DTLS/SRTP ═════════════════  H.264 视频 ▶，◀ input DataChannel
```

| 方面 | 实现 |
|---|---|
| WebRTC | `str0m` 0.25，纯 Rust 加密后端（不依赖 OpenSSL）。被控端是 ICE-lite，只给一个 host 候选：浏览器访问网页时用的那个地址 |
| 视频 | 原有采集和 VideoToolbox H.264（High）编码，缩放到 1920×1200 以内，60 fps。浏览器的 PLI 映射为强制关键帧，TWCC 带宽估计映射为 `set_bitrate` |
| 输入 | `input` DataChannel 上的小 JSON：键为 HID 用法（页面按 `KeyboardEvent.code` 映射），位置为画面比例。被控端逐条校验后交给现有 `InputSink`。每个按键事件都按其修饰键标志补齐 Shift/Ctrl/Alt/Cmd 的状态 |
| 配对 | `nexa_auth::browser`（被控端）与 `crates/nexa-web-pake`（浏览器，WebAssembly，无 JS 胶水、无导入）。与原生端同一套 SPAKE2、转录和确认值，身份换成双方的 DTLS 证书指纹，HKDF 盐换成独立的 `nexa/1 browser dtls-sha256`。一次性码和固定密码都可以：固定密码在浏览器里用和原生端相同参数的 Argon2id（64 MiB、3 轮）处理，桌面浏览器约 0.1 秒 |
| 固定密码 | 被控端可以设一个固定密码，和一次性码同时有效：对方在同一个输入框里填，能当作一次性码的就是一次性码，否则是密码，所以密码不能长得像一次性码，且至少 8 位。被控端只在钥匙串里保存 Argon2id 的结果（`nexa-agent set-password`，从标准输入读，应用里在“允许别人控制本机”下设置）。输错次数和原生端共用一套限制。用固定密码连接不弹确认窗口（这是机主自己的入口），直接进入，顶部提示条照常显示、可随时断开；正在有会话时仍会询问是否接管。用一次性码连接仍需本机确认 |
| 只填设备 ID | 经服务器连接时，码和密码都可以不填（`auth:"request"`）：被控端照样弹确认窗口，并在窗口里注明“只凭设备 ID 请求，无法核实对方身份”，点允许才连。没有共享秘密，就没有 SPAKE2 把两端的 DTLS 指纹绑在一起，所以对方是不是那台电脑，只能信任服务器；网页会说明这一点。直连（不经服务器）不接受这种请求。原生应用同理（`Auth::Request`），且只能配设备 ID：主机的公钥来自服务器，QUIC 对端必须是这把钥匙。这类请求和输错码共用一套频率限制，不会被保存为配对 |
| 重置设备 ID | 设备 ID 由服务器根据主机公钥算出，不存任何状态。主机可以在注册时附带一段随机种子（`Register.id_seed`，最多 32 字节，计入签名），种子不同 ID 就不同。应用里点设备 ID 旁的“重置”并确认后，运行 `nexa-agent reset-device-id`，在数据目录写入新的 `device-id-seed`，再重启托管；旧 ID 立即失效。注意：带种子的注册需要新版服务器，旧服务器会因签名不符而拒绝 |
| 先直连再中转 | 经服务器连接时，被控端先只给出它在服务器 TURN 上的中转地址，浏览器也不再限定只走中转（`iceTransportPolicy: "all"`）。被控端放行（确认窗口点“允许”或固定密码）之后，才在每个局域网 / Tailscale 地址上各开一个 UDP 端口，作为候选地址补发给浏览器（`{type:"candidates"}`）。同一局域网或 tailnet 里，浏览器会切到直连（实测 192.168.0.70，约 1 ms）；不通就继续走中转。放行之前，对方拿不到本机任何地址 |
| 多人同时连接 | 最多 4 人同时连接同一台 Mac（应用和浏览器合计），每人都能看能操作，各自单独确认，不会互相顶替；同一台设备重连时只替换它自己原来的会话。每人一条顶部提示条，可单独断开（`Disconnect{id}`，id 为 0 时全部断开）。谁离开就只结束谁的会话：应用端 QUIC 关闭立即结束、断网 10 秒内超时；浏览器端关页面时发 `bye`、WebSocket 断开或 ICE 断开都会立即结束。每人各有一套采集和编码 |
| 命令行（终端） | 网页顶栏的“终端”按钮打开这台 Mac 的命令行：用户的登录 shell（`$SHELL -l`，在主目录启动，`TERM=xterm-256color`），跑在伪终端上（`crates/nexa-term`）。页面用 xterm.js 6.0（MIT，放在 `web/vendor/`）显示，走 WebRTC 数据通道 `term`：按键和输出都是二进制消息，`{t:"r",c,r}` 调整大小，`{t:"x",why}` 表示 shell 已结束。输出积压超过 256 KB 时暂停读取，让 shell 慢下来。终端是单独一项权限：确认窗口里默认不勾；用固定密码进来的是机主本人，直接给。关闭终端或会话结束时，对 shell 所在的整个进程组挂断（SIGHUP），1.5 秒后还在的进程直接杀掉，不留后台进程。因为 xterm.js 会自己插入 `<style>`，页面 CSP 放开了 `style-src 'unsafe-inline'`，脚本仍然只能来自本页 |
| 连接时选屏幕或终端 | 连接页有“屏幕 / 终端”选择（记在浏览器里）。选终端时 offer 带 `view:"terminal"`：被控端不开采集和编码，确认窗口里命令行一项预先勾上，`accepted` 里 `video:false`，页面直接全屏显示命令行，shell 退出即结束会话。被控端没有屏幕（命令行被控端，见 `docs/TERM_HOST.md`）时，无论选什么都是终端；终端没被允许则以 `noterminal` 拒绝 |
| 分辨率 | 网络面板里可选：自动（默认，按浏览器窗口的实际像素，最高到对方屏幕的分辨率，Retina 屏上不再被放大发虚）、原生（对方屏幕的原始像素）、1080p、720p（限制行数，宽度按屏幕比例）。页面经输入通道发 `{t:"s",m,w,h}`，自动模式下窗口大小变化 600 ms 后再发一次。画面大于 1920×1200 时码率上限按像素数提高，最多 50 Mbit/s；分辨率选“自动”时，“弱网”或自动降级仍保持小尺寸，手动选的分辨率则一定照用（以前自动降级后选 1080p 不起作用）。顶栏同时显示帧率 |
| 多显示器 | 被控端有两个及以上显示器时，顶栏出现“显示器 N”按钮，点开列出各显示器（名称、像素，主显示器排第一并标“主显示器”），点一个就切换。**一次只显示一个**，不在同一页面里同时显示多个显示器。`accepted` 带 `displays:[{n,w,h,id}]`（名称、像素、显示器标识）和 `display`（当前序号）；序号就是 `WebHost::displays` 里的位置，和原生端 §3.6 的 `Display.id` 一样。页面经 input 通道发 `{t:"d",i,id}`；被控端按 `id` 找显示器（列表在页面拿到之后可能因插拔显示器而变，按序号会切到别的屏），没有 `id` 时才按序号；被控端（采集线程上）重新读取显示器列表，先放掉旧的采集和编码（Windows 的 DXGI 桌面复制每个进程每个显示器只能有一个），再按当前的画质和分辨率为新显示器建立；成功后键鼠坐标（全局坐标 = 该显示器原点 + 比例 × 它的点尺寸）和光标位置都改以新显示器为准。成功或失败都回 `{t:"d",i,pts,list,err}`：`i` 是现在显示的序号，`pts` 是它的点尺寸（页面按它画光标），`list` 是重新读到的列表，`err` 为 `unavailable`（没有这个显示器，什么都不变）或 `failed`（采集不起来，退回原来的显示器，和原生端一样；连原来的也起不来时，先回 `failed` 再结束画面，页面不会对着冻住的画面一直等）。连着点几次只按最后一次切。切换期间页面把旧画面调暗、不发鼠标位置和按下，并先松开所有按住的键，等被控端回话（10 秒没回话按失败处理）。只看不控的浏览器也能切换（和画质一样，与输入无关）；纯终端会话没有画面，不处理这条消息。演示主机（`cargo run -p nexa-web --example demo`）带第二个橙色的显示器，可以试切换；`NEXA_DEMO_ONE_DISPLAY=1` 时只有一个 |
| 网络与画质 | 顶部显示连接方式（局域网直连、Tailscale、经服务器中转、公网直连）和往返时延，颜色表示好坏；点开有丢包、码率、帧率、分辨率。画质可选“自动 / 清晰 / 均衡 / 弱网”，被控端据此换分辨率、帧率和码率上限（弱网：1280×800、15 fps、≤1.5 Mbit/s）。“自动”下，带宽估计持续 3 秒低于 1.2 Mbit/s 就降到 1280×800、30 fps，持续 8 秒高于 3.5 Mbit/s 再恢复。被控端把当前画质的码率上限告诉 str0m 作为想要的码率，带宽估计才会探测上去（以前没告诉，估计停在起始的 8 Mbit/s 附近，画面静止时还会往下掉，自动模式随之降级）。局域网（浏览器连的是本机的私有地址）不用 str0m 的带宽估计，也就不按它限速：画面基本静止时发的数据很少，Wi‑Fi 的一次抖动就会把估计砍到几百 kbit/s，str0m 再按这个速度发每一帧，结果局域网里 3 ms、零丢包也只有 1280×720、0.3 Mbit/s，而且滞后。局域网改看浏览器每秒的接收报告：没有丢包、往返时延没有比一分钟内最低值高出 60 ms，码率就乘 1.5（约 3 秒从 8 到 25 Mbit/s）；丢包达到 2% 或排队连续两次报告才乘 0.7，一次抖动不算。经服务器中转、公网和 Tailscale 仍用 str0m 的估计。被控端每 5 秒在 agent.log 写一行浏览器画面的统计 |
| 限制 | 一次性码与原生端共用，次数限制也共用；同一来源每分钟最多 8 次握手；同时只允许一个会话（浏览器和原生端互斥） |
| 确认 | 走原生端同一个确认窗口，标明“浏览器”，提供“查看”“键盘鼠标”和“剪贴板”三项（剪贴板默认不勾），不保存设备 |
| HTTPS | 同一端口按第一个字节区分 TLS 和明文；明文请求一律 308 跳转到 HTTPS。证书默认由被控端自签，按本机地址、`.local` 名和 Tailscale 名签发，地址不变就一直复用，浏览器只在第一次提示。数据目录里放 `web-cert.pem` 和 `web-key.pem`（例如 `tailscale cert` 签发的）就改用它，不再有提示。应用里列出证书 SHA-256 的开头，供核对 |
| 输入法 | 键盘输入经一个隐藏的文本框：输入法组合中的按键不发出，组合完成后的文字以 `{t:"s"}` 发给被控端，按 Unicode 输入。文本框跟随鼠标位置，候选窗出现在附近 |
| 手机 | 轻点 = 单击，长按或双指轻点 = 右键，单指拖动 = 按住左键拖动，双指拖动 = 滚动，双指张合 = 放大本地画面（不影响被控端）。“键盘”按钮唤出系统键盘，并显示 Esc、Tab、方向键和可锁定的 Ctrl、⌥、⌘、Shift；键盘弹出时这排按键跟着上移 |
| 剪贴板 | 文字双向，单条最多 192 KiB；图片从浏览器到被控端：不超过 2 MB 的 PNG 和 JPEG 原样发；更大且没有透明的（多是照片）转成质量 90% 的 JPEG（省下至少三成才用），其余转成 PNG；最多 16 MB。以二进制消息每块 64 KiB 发，浏览器里排队的不超过 256 KiB，所以同一通道上的鼠标和按键最多只等这么一点；`{t:"ce",n,f,s}` 结束（`f` 是 png 或 jpeg，`s` 是同时复制的文字），被控端把 JPEG 转回 PNG 再写入剪贴板。旧页面的 base64 分块 `{t:"ci"}` 仍然接受。都走 input 通道：浏览器里按粘贴键时，先把浏览器剪贴板的内容发过去写入被控端剪贴板，再发粘贴键（带上被控端的粘贴修饰键），所以对方粘贴出的一定是刚复制的内容。写入和读取被控端剪贴板在单独的线程上，读剪贴板慢或出错不会拖住键盘鼠标；写入时输入线程最多等 1 秒（图片 3 秒）。被控端上新复制的文字（会话开始前的不算，密码管理器标为敏感的不发）写入浏览器剪贴板；浏览器不允许时显示“复制到本机”按钮 |
| 按住的键 | 有键或鼠标键按住时，页面每秒发 `{t:"ks",c:[…]}` 说明按着哪些键，被控端照原生端的按键状态同步处理：没说的键松开，说了的不会因 3 秒无同步被松开（长时间拖动、一直按着 Shift）。Mac 上的浏览器在按住 ⌘ 时松开别的键不发 keyup，所以 ⌘ 抬起时页面把这期间按下的键一并松开 |
| Ctrl 与 ⌘ | 浏览器和被控端的快捷键修饰键不同时默认对调：被控端是 Mac、浏览器不在 Mac 上时 Ctrl 当作 ⌘（Windows 键当作 Ctrl）；浏览器在 Mac 上、被控端是 Windows 或 Linux 时 ⌘ 当作 Ctrl（Control 键当作 Windows 键），⌘C/V 照常复制粘贴。页面顶部可以关掉；iPhone、iPad 上不显示这个开关 |
| 网页安全 | 严格 CSP（只允许本站脚本和 WebAssembly 编译）、`nosniff`、`no-referrer`、HSTS；`/ws` 只接受来自本站页面的 Origin |
| 开关 | 默认关闭。应用：主窗口底部“允许浏览器连接”；命令行：`nexa-agent --web <ip:port>`。`--relay-only` 时不开放 |

**已知限制：**

- 自签证书会让浏览器第一次打开时警告；只有核对过指纹，才能排除第一次就被人替换。用自己的证书（如 `tailscale cert`）可以避免。
- 浏览器拦不住的系统快捷键（Cmd+Tab 等）发不出去。
- 被控端复制的图片还不会发到浏览器（只发文字）；声音、文件传输还没有。
- 多显示器一次只能看一个（有意如此）。切换请求发出前已在途的键鼠输入仍按旧显示器处理；页面收到被控端回话后、新画面的第一帧到达之前（通常几十毫秒）点在旧画面上的位置，会按新显示器换算。

## 12. 从任何网络连接（经自建服务器）

浏览器连不到被控端时（不在同一网络，也没装 Tailscale），可以经自建的 `nexa-signal` 连接，前提是被控端已经注册在这台服务器上（有 9 位设备 ID），并打开了“允许浏览器连接”。服务器的 `[web]` 配置打开后：

- 服务器在信令端口上提供同一份网页（`crates/nexa-web-page`），网页通过 `GET /mode` 得知自己来自服务器，于是多要一个设备 ID；
- 浏览器连 `/web`，先说 `{type:"hello", id}`；服务器按设备 ID 找到被控端，经被控端已有的信令连接发 `BrowserOpen`，之后把双方的消息原样转发（`BrowserText`/`BrowserClose`）。消息内容和 §11 的直连协议完全一样；
- 画面和输入走 TURN。服务器在第一个 STUN 端口上同时提供 TURN（`crates/nexa-turn`），给浏览器和被控端各发一组只用于这次连接、24 小时后失效的凭据。浏览器只用中继候选；被控端在 TURN 上分配一个地址，作为它唯一的候选。

```
浏览器                       nexa-signal                         被控端
  GET https://服务器/  ──▶  网页
  WS /web hello{id} ────▶  按 ID 找到被控端 ── BrowserOpen ──▶  在 TURN 上分配地址
         ◀── routed{TURN 地址和凭据}
  offer / auth … ◀═══════  原样转发（BrowserText）  ═══════▶  同 §11：SPAKE2 绑定双方 DTLS 指纹
  媒体 ◀══ TURN 分配 B ══ 服务器内部转交 ══ TURN 分配 H ══▶
```

**安全。**服务器只转发：配对把一次性码绑定到双方的 DTLS 指纹上，服务器既冒充不了被控端，也冒充不了浏览器；画面和输入经 DTLS/SRTP 端到端加密。它能看到谁在什么时候连接、流量多大。TURN 不是开放中继：分配到的中继地址是虚拟的，数据只在同一台服务器的两个分配之间转交，而且接收方必须先授权，发往其他地址的一律丢弃，所以不能借它访问互联网上的其他主机。

**部署。**见 docs/DEPLOY.md 的 `[web]`：信令端口（TCP）和第一个 STUN 端口（UDP）放行即可，不需要额外的端口段。

**限制。**目前只走 UDP；所在网络封锁 UDP 的浏览器连不上（TURN over TCP/TLS 还没做）。所有画面都经过服务器，占用服务器带宽。被控端开着 `--relay-only` 时不提供浏览器访问。
